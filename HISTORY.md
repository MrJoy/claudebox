# History

## 0.5.0 - 2026-08-31

* **A PR nobody has touched is no longer re-reviewed.** The cycle used to walk every candidate PR every time, so with the persona multiplier a quiet repo still spent (PRs x that PR's mode's personas) provider sessions per cycle proving nothing had happened. The gate now sits between enumeration and the walk: a PR runs only when its head commit moved, a comment or review arrived that claudebox did not post itself, an inline diff comment did the same, or its label flipped it between code and plan mode. Editing the title, body, or base branch does not count.
* **Own comments are told apart from everybody else's by the `-claudebox` marker, not by author login.** `personas/code/_shared.md` and `personas/plan/_shared.md` already told every persona to sign that way; the marker is now load-bearing rather than cosmetic, and both files say so. Login was rejected because claudebox commonly runs under the operator's own PAT, where matching on login would read every comment the operator writes as claudebox's own and the comment trigger would never fire for the person most likely to want it.
* **The lookup is two stages, and a quiet cycle costs what it costs today.** Stage one widens the `gh pr list`/`gh pr view` call every cycle already made to carry `headRefOid` and `updatedAt` alongside labels, at no extra request. Stage two, a `gh pr view --json comments,reviews` plus a `gh api .../pulls/N/comments` for inline comments, runs only for a PR whose `updatedAt` moved since the last time it ran, so a cycle in which nothing happened makes the one request it always did. `updatedAt` gates the lookup and is deliberately outside the fingerprint itself: it moves on edits this design does not care about, and including it would turn a typo fix into a full persona fan-out.
* A stage-two failure fails open — the PR is reviewed rather than skipped, with a WARN naming it — because the mode is already known from stage one and the worst case is a redundant pass, unlike the `ids` selector's mode lookup, which skips on failure because a wrong-mode review posts comments nobody can take back. The failed lookup is still cached against that `updatedAt`, so a persistent `gh` outage costs one stage-two call per poll instead of repeating it forever.
* **`SETTLE_SECONDS` (default 30) batches a burst.** A PR whose newest change is younger than the setting is left off the candidate list for this poll, with nothing recorded against it, so the next poll reconsiders it from scratch rather than treating the wait as a lookup already made. A handful of pushes in a row now costs one review instead of one per push. A negative age — the container clock behind GitHub's — runs rather than settles, so clock skew costs the batching and never the review.
* **`REVIEW_INTERVAL_SECONDS` is a poll interval now, and its default drops from 300 to 60.** A poll that finds nothing changed is cheap enough that polling more often is the right trade, and the interval is what now bounds the delay between a push landing and the first review of it. `REVIEW_ON_CHANGE=0` is the escape hatch back to reviewing every candidate on every poll; an operator who reaches for it should raise `REVIEW_INTERVAL_SECONDS` back toward 300, since the lower default assumed most polls would review nothing.
* The gate is a pure narrowing of `pairs_to_run`: a pair a limit or a failure cut short still runs on its own terms regardless of what its PR's fingerprint says, and a pair with no session — first sight, a session `_record_failure` dropped, a `MAX_PASSES_PER_SESSION` rotation — runs unconditionally, because none of those paths needed to know the gate exists. The fingerprint map lives in memory beside the session map and is deliberately not persisted: a fingerprint that survived a restart the session map did not would leave a fresh session believing, from the fingerprint alone, that it had already read a PR it has never seen.
* New module `reviewer/signals.py` holds the fingerprint, the marker test, and the settle arithmetic, all pure; the GitHub calls stay in `gh.py` and the state that outlives a cycle stays on `Supervisor`. `test-personas.sh`'s `gh` stub now advances `headRefOid` and `updatedAt` between its two cycles, since the suite exists to prove a resumed pass still carries its persona and the gate would otherwise leave cycle two with nothing to run.
* **A whole-branch review found the gate had three definitions of "unchanged" instead of one, and they disagreed.** `pairs_to_run`, the debt a cut group leaves behind, and the debt the groups a cycle never reached carry forward were each their own inline expression. A usage limit that cut a group after the gate had already excused some of its personas re-owed those personas anyway — a wasted resumed session, spent on a PR nothing happened to, at the exact moment the provider budget had run out. `Supervisor._gate_holds(pair, signal)` is now the one predicate; `pairs_to_run` and the renamed `debt_for` (formerly `unreached_debt`, whose old name went false the moment the cut group started calling it too) both call it and neither restates it. The fix reaches the three-strikes exit as well as the limit exit, since a dead provider must not re-owe a persona with nothing to review either.
* **A dead or flapping provider used to be retried at the ordinary poll interval, with a fresh session every time**, because the three-strikes abandonment cleared `was_limited` and every session it touched was already dropped. At a 60s poll that is a full fan-out every minute against an endpoint that isn't answering. `run_cycle` now returns why it stopped — `CYCLE_OK`, `CYCLE_LIMITED`, or `CYCLE_UNHEALTHY` — instead of a bare bool, and both non-OK outcomes wait `LIMIT_BACKOFF_SECONDS` rather than the interval. `CYCLE_OK` is the empty string, so every existing truthy/falsy check on the return kept working unchanged.
* **A quoted signature is a human, not claudebox.** GitHub's Quote reply button copies the quoted comment verbatim behind `> `, so a human disputing a finding used to carry the `-claudebox` marker and be read as claudebox's own — the design's own spec had accepted this as a known gap. `signals.is_own` now drops lines starting with `>` before testing for the marker, so a reply that quotes a finding and adds prose reads as human, and a reply that quotes and then signs still reads as claudebox because the unquoted half decides.
* **Stage two's inline-comment lookup is capped, not paginated.** It used to walk every inline comment ever posted on every PR whose `updatedAt` moved — which, since claudebox's own comments move it, is every PR claudebox reviews, on the next poll after every review, at a poll interval that just dropped 5x. It now asks for the 30 newest (`sort=created&direction=desc&per_page=30`), enough to find the newest unsigned comment in any realistic case, without risking the container's GitHub rate limit on a long-lived PR's comment history.
* `change_reason`'s `prior` fingerprint is now taken from the pairs actually running rather than from the whole group, so a mixed group — one persona rotated by `MAX_PASSES_PER_SESSION`, another gated — cannot log a head change against a fingerprint that belongs to a pair sitting this cycle out.

## 0.4.0 - 2026-08-30

* **A PR's personas now review it at the same time.** The cycle used to walk a flat list of (PR, mode, persona) pairs one at a time, so widening the persona set cost wall clock in proportion. It now builds one group per PR, hands that group's pairs to a thread pool, waits for all of them, and only then moves to the next PR. The sessions per cycle are unchanged — this buys latency, not allowance. Blind personas were always unordered and the working clone was always meant to be read-only, which is what made the fan-out available; what changed is that the reasons for declining it turned out to be addressable rather than inherent.
* **The PR is the unit of fan-out, and the barrier is the reason.** Running every candidate PR's passes at once would put the whole list's usage-limit pressure on the provider in one instant, which is the objection that kept this sequential in 0.1.0. A per-PR group bounds that to one PR's worth of passes, and it gives the cut-short accounting somewhere to happen: a limit reported by one persona cannot recall its in-flight siblings, so the group finishes and the cycle stops after it. Nothing is killed, ever. A killed pass may have posted some findings and not others, and its session id — recovered from the stream as it arrives — is not reliably in hand when it dies.
* `MAX_CONCURRENT_PASSES` (and `--max-concurrent-passes` on the launcher) caps how many of a group run at once. Unset or `0` is all of them; a value that is not a non-negative integer is a startup error. `1` is a one-worker pool rather than a separate sequential branch, deliberately: a second code path would drift from the concurrent one and would silently invalidate every ordinal assertion in `test-personas.sh`.
* **The cut-short bookkeeping grew a second half.** 0.1.0 remembered the pair a limit stopped at and resumed there. That is now a group rotation plus a debt: `cut_group` says which PR the next cycle starts after, and `owed` says which personas did not get to run — the ones the limit prevented, plus every pair of every group the cycle never reached. A group that owes something runs only what it owes, since the rest of it already ran. Serving the debt first instead of rotating reads as the obvious thing and is a trap: a pair that reports a limit on every attempt would re-cut the cycle at the head of the list forever and nothing else would ever be reviewed again. Both are rebuilt from the cycle's own groups at the end of it, so a debt whose PR has closed does not survive. Both are still in memory; persisting them across a restart is still deferred.
* **Sharing one working copy between concurrent reviewers needed two new defenses, and they arm together.** Every pass runs `claude` in the same clone, so one persona's `git checkout` changes the diff its siblings are reading mid-review. The reviewer is now told the working copy is shared and to read the change through `gh` — and the supervisor drops the write bit on the clone's `.git` for the whole run, lifting it only for the cycle's own fetch, so a persona that tries anyway gets a permission error rather than corrupting a review. Both are gated on `min(MAX_CONCURRENT_PASSES, that mode's persona count) > 1`, evaluated per mode and reading an unset or zero cap as the persona count, so a mode running one persona gets byte-identical prompts to the old loop and `MAX_CONCURRENT_PASSES=1` collapses every mode at once. A missing `.git` when the lock should arm is a hard startup error: reaching it means the prompt has already told six personas the clone is protected.
* The lock covers `.git` **and every directory under `.git/refs`**, and never `.git/objects`. The first draft covered `.git` alone, and its review refuted that empirically: against a clone locked that way, `git update-ref refs/remotes/origin/main HEAD` and `git notes add` both return 0, and both change what a sibling reads — the first empties `git log origin/main..HEAD` so the PR appears to contain nothing, the second injects chosen text into every sibling's `git log` and `git show`. The object store stays out because that walk is O(object count), which is the cost 0.2.1's mount narrowing exists to avoid; refs is O(ref count), seven directories against a couple of hundred on this repo.
* **One exception to the verbatim-operator-prompt guarantee, the first since it was written.** The shared-worktree constraint is appended to a `REVIEW_PROMPT`/`FOLLOWUP_PROMPT` override as well as to the defaults, after the operator's own `_SUFFIX` so their last word cannot displace it. Every stanza before it applied to the defaults only, on the principle that an operator's prompt is theirs. This one is different because the operator whose prompt is being edited is not the person who pays for a persona writing to the clone — its siblings are. `MAX_CONCURRENT_PASSES=1` removes it, which is the escape hatch for anyone who wants the old guarantee back unconditionally.
* `entrypoint.sh` now `chmod u+w`s the clone's `.git` before its own git setup. A container restarted by `--restart unless-stopped` meets a clone the supervisor locked and never unlocked, and `git remote set-url` writes through `.git/config.lock`; without this the second boot dies under `set -e` and the restart policy turns that into a silent crash loop.
* Two things 0.3.0 built for a concurrency that did not exist yet now carry weight. Log lines from inside a pass are prefixed `[#12 code/sage]`, and `common.log` holds a lock across the write, so passes interleave between lines and never inside one — ordering across personas is not deterministic, ordering within a persona is. And `check_litellm` reaps only the translator and normalizer pids rather than `waitpid(-1)`, because a wildcard reap would collect a review pass's own `claude` and steal the exit status its `Popen` is waiting for; one pass at a time kept that window narrow, and concurrent passes hold it open.

## 0.3.0 - 2026-08-30

* **The review loop is Python.** `entrypoint.sh` was two programs sharing a file. One builds an environment for a child process, a job shell handles well. The other is a stateful supervisor holding structured results per task, which shell has no good way to represent. The first stays where it was — hardening checks, `gh`/`git` auth, provider wiring, the working clone, the LiteLLM translator — and now ends in `exec python3 /opt/claudebox/reviewer/review_loop.py`. Everything downstream of that lives in `reviewer/`: prompt assembly, persona resolution, PR enumeration and label routing, the session map, dispatch, limit classification, resume bookkeeping. Environment crosses the boundary and nothing else does.
* Every defect ever recorded against this harness lived in the half that moved. A `MODE_PERSONAS` expansion that word-split and glob-expanded once an array had been flattened into a space-joined string, so a persona basename with a glob character killed the loop mid-cycle. A `gh pr view --json labels` that exited 0 with nothing useful, dropping a PR with no log line at all. An unguarded `.number` in a jq filter, producing a candidate PR literally named `null`. Three `case "$mode"` dispatches with no `*)` arm. Those are all one thing: shell cannot tell absence from emptiness, and deciding what a piece of missing input means is most of what the loop does.
* **Behavior is otherwise unchanged, and five departures are deliberate.** The `all`/`assignee`/`search` enumeration arms now log a WARN when `gh pr list` fails, where a failure used to be indistinguishable from "no open PRs", and the WARN carries the tail of `gh`'s own stderr, which `capture_output` would otherwise swallow. Log lines emitted during a pass carry a `[#12 code/sage]` prefix, and stream lines carry a timestamp they did not have. `MAX_CYCLES` replaces the trick that used to end a run in the test suites, a stubbed `sleep` exiting non-zero into the entrypoint's `set -e`, which the port left with nothing to hook because the interval is a `time.sleep()` inside Python now. `REVIEW_INTERVAL_SECONDS` is validated at startup, so a value carrying a unit suffix refuses to start where it used to work: the shell passed it straight to `sleep`, which accepts `5m`, and `.env.example` has always said seconds, so the config meant five seconds to everyone reading the docs and five minutes to the container. And `PERSONAS=" all "` selects every persona rather than dying on `unknown persona 'all'`; the shell compared the untrimmed value, which made surrounding whitespace an error message about a name nobody typed.
* `MAX_CYCLES` bounds the number of cycles before the process exits. Unset or `0` is forever, which is what an unattended container wants; `1` is a genuine one-shot, which is what both bash suites set. The launcher passes it to nothing, so a foreground `claudebox.sh test` still runs until you interrupt it unless your env file sets it. A value that is not a non-negative integer is a startup error.
* The PR selector and both modes' persona sets are resolved twice: once by `entrypoint.sh` through `python3 .../review_loop.py --check`, before `gh` auth, the working clone and the translator's blocking startup, and once by the supervisor itself after the `exec`. Same code, same message. The pre-flight is what keeps a typo'd `PERSONAS` from costing a network clone of the whole repo and up to 120 seconds of LiteLLM startup on every restart under `--restart unless-stopped`, which is what the shell's own fail-fast ordering bought and the port briefly lost. `--check` reads only what the environment holds at that point, so it cannot come to depend on anything the shell exports on its way to the exec.
* A pass that fails to *spawn* is an ordinary failed pass. `subprocess.Popen` raises for `EAGAIN` against `--pids-limit`, `ENOMEM` against `--memory`, and a `claude` that is not on `PATH`; the shell read `PIPESTATUS[0]` and saw a non-zero rc for all three. Unguarded, the exception exits PID 1, and the session map lives only in memory, so the restart makes every pair re-post findings it already posted. `git fetch` and the `gh` calls behind PR enumeration are guarded the same way, matching the `|| true` / `|| log WARN` they were ported from.
* New suite `test-python.sh`, 194 unit tests over the decisions the loop makes: prompt assembly, persona resolution, selector and label routing, limit classification, the stream formatter, and the cycle bookkeeping. The four assembled prompts are pinned byte-for-byte against fixtures captured from the pre-port entrypoint, so the port could be checked rather than eyeballed, and the stanza text was lifted across by a script (`tools/extract-stanzas.py`) rather than retyped. Both bash suites run unchanged against the new loop, which is what the port was judged by; `test-providers.sh` grew a `python3` stub that dispatches on the script path, because the normalizer must be faked and the supervisor must be real.
* `reviewer/` is standard-library only, matching `workersai-shim.py`, so the image installs nothing new for it. It is copied in root-owned, like the LiteLLM install: the reviewer account reads this code and must never write it, and under `--restart unless-stopped` a writable supervisor would be a persistence vector across restarts for a session that already runs with `--dangerously-skip-permissions`.

## 0.2.1 - 2026-08-28

* **The launcher now mounts the host repo's `.git`, not the host repo.** `claudebox.sh --repo PATH` binds `PATH/.git` read-only at `/repo/.git`, and `entrypoint.sh` local-clones that. The startup clone was always the only thing that read the mount; nothing in the entrypoint touches it again for the rest of the container's life. Mounting the whole tree to serve one read left every ignored file in it (a Unity `Library/`, nested worktrees, build output) reachable by a reviewer that decides to go wandering, and on a VirtIO-backed mount walking a tree that size can pin file descriptors until the host falls over. This was reported twice from a real Unity checkout.
* The mount point convention did not change: it is still `REPO_PATH`, default `/repo`, with the object store inferred at `$REPO_PATH/.git`. That is what makes a hand-rolled whole-repo `docker run -v /path/to/repo:/repo:ro` keep working with no compatibility branch behind it, since its `.git` is at the same path either way. Seed selection is `$REPO_PATH/.git`, then `$REPO_PATH` itself for a bare repo mounted directly, then `gh repo clone`.
* "Mount the primary repo, not a worktree" stops being advice and becomes a startup error. In a worktree `.git` is a file rather than a directory, so the guard that finds the object store also catches it, and the launcher dies naming the reason instead of building something structurally unusable. A bare repo as `--repo` is refused for the same reason, with its own message.
* `test-providers.sh` grew three cases covering the seed order, which meant reaching a block the suite had never run: it pre-creates the working clone in every other case. `PRESEED_WORK=0` leaves that out, and the `git` stub now answers `rev-parse --git-dir` honestly rather than succeeding at everything, so which seed was chosen is something the suite can actually observe.

## 0.2.0 - 2026-08-25

* **A correction.** advocate's personas are *plan-review* personas: they were written to interrogate a proposal before the work happens. 0.1.0 shipped them as the mechanism for reviewing pull requests in general, which misread what they are for. Sage asking whether the fundamental approach is sound, and SME asking whether the problem is correctly understood, cost almost nothing to act on before code exists, and on a finished PR the only honest answer to either is "start over". So review **mode** is now a first-class axis alongside PR and persona, and claudebox does both jobs.
* A plan arrives as a pull request whose diff is the plan document, which is what keeps the change small: the loop, the four PR selectors, the session map, the usage-limit handling and the `gh pr comment` output channel are all untouched. A PR carrying `PLAN_LABEL` (default `plan`) is reviewed in plan mode; every other PR is code mode, so an operator who never labels anything sees exactly 0.1.0's behavior. Routing is by label rather than by a path heuristic or a classifier pass: a label is explicit, per-PR, set by someone with triage rights, and puts no nondeterministic decision inside the harness's control flow.
* Mode is decided inside `enumerate_candidate_prs`, which now emits `number<TAB>mode` so nothing downstream asks GitHub a second time. For `PR_ALL`/`PR_ASSIGNEE`/`PR_SEARCH` the labels ride along in the `gh pr list` call already being made; `PR_IDS` has no list call behind it, so it costs one `gh pr view` per PR per cycle.
* **A failed label lookup skips that PR for the cycle**, with a WARN, and never falls back to code mode. This is the decision most likely to be questioned later, so: a wrong-mode review posts real comments on a real PR and cannot be taken back, where a skip is one log line and a retry on the next cycle. The `ids` arm checks its output is non-empty rather than trusting an exit status, because a `gh` that exits 0 with nothing useful would otherwise drop the PR with no warning at all.
* `PERSONA_DIR` is now a parent holding `code/` and `plan/`, each with its own `_shared.md` and all six persona bodies. Both trees resolve at startup whether or not any PR is labeled, so a broken plan persona kills the container at boot instead of surfacing the first time somebody adds a label. A flat `PERSONA_DIR` is a hard startup error naming the layout it expected; this breaks 0.1.0's mount-your-own contract, and nothing has shipped off that contract.
* Per-mode defaults: code keeps `red_team,adversarial,sme,sage` and plan runs all six, selected by `PERSONAS` and `PLAN_PERSONAS`. The code cut needs no new argument, since it is the reasoning 0.1.0 already wrote down: `user` and `good_friend` were authored against designs and whole projects, and plan review is where they finally have something to bite on.
* Session keys grew a segment, `"$pr:$mode:$persona"`, so a PR whose label changes orphans its old sessions and starts fresh under the new mode. That is intended: a code-mode session's accumulated history is the wrong context for reviewing the same branch as a plan. `--resume` matters more in plan mode than in code mode, because feedback on a plan produces a revised plan pushed to the same branch, and a persona reading revision two in the context of what it said about revision one is exactly the shape the loop was already built for.
* Plan prompts drop the test stanza (there is no implementation to mutate), keep the gh and Linear stanzas, and add a plan stanza that says what **not** to flag as well as what to review: a code-shaped reviewer handed a design document will otherwise report missing error handling in code nobody has written. Overrides are `PLAN_REVIEW_PROMPT`, `PLAN_FOLLOWUP_PROMPT`, and their `_SUFFIX` forms; the bare names still mean code mode. Neither the four code prompt variables nor their plan counterparts is quote-stripped, since a quote at either end of free text can be content; the code four were never on that list, and the plan four were taken back off it to match.
* **The importer writes the same body into both trees, and there is deliberately no divergence detection.** The second decision worth flagging for later. advocate has one body per persona, so `tools/import-advocate-personas.py` cannot invent two, and a hand edit in one tree is something a re-import would clobber. Its docstring already says to run it once and commit the output, so a re-run produces a diff that gets reviewed before it is committed, and a hand edit shows up in that diff as a reverted line to keep. A detector buys very little over reading a diff somebody was going to read anyway.

## 0.1.0 - 2026-08-21

* Reviews now run as **adversarial personas** rather than as one generalist reviewer, borrowed from [advocate](https://github.com/jmcentire/advocate) — Red Team (survive assault), Adversarial (hold under challenge), Sage (simplify), Subject Matter Expert (peer sign-off), and opt-in User (navigate it cold) and Good Friend (the 3am test). advocate itself cannot be used here: it calls provider APIs directly, so it cannot run against a fixed-price plan, which is the whole reason claudebox drives the CLI. Definitions ship as files (`personas/*.md`, `PERSONA_DIR`) imported by a committed script, with advocate's JSON output contract stripped (claudebox posts `gh` comments) and its "silence from you is a strong signal" rule kept. `--persona` / `PERSONAS` selects the set; an unknown name is a startup error, because a typo that silently narrowed the review to one persona would read as a working run.
* One session per PR **per persona** (`PR_SESSION` keyed `pr:persona`, so `MAX_PASSES_PER_SESSION` rotates per pair). The persona travels in `--append-system-prompt`, which keeps an operator-supplied `REVIEW_PROMPT` verbatim, and is re-passed on every single pass: measured, the flag does **not** survive `--resume`, so passing it once would make cycle one adversarial and every cycle after it the old generalist wearing a persona's name in the log.
* Personas are blind to each other, deliberately. Nothing tells a persona to skip what another already raised: that anchors it to a review it did not do, and avoiding that flavour of group-think is why this tool exists. Two angles of attack hitting the same thing is a signal it deserves two comments. Comments are signed `-claudebox (<Persona>)`.
* Usage and rate limits are now a distinct failure. A pass that hits one keeps its session, ends the cycle instead of walking the remaining personas into the same wall, and waits `LIMIT_BACKOFF_SECONDS` (default 1800). The old path dropped the session, which under a limit meant the next cycle re-read every PR and re-posted findings already posted — spending more of the allowance that had just run out. Multiplying sessions per cycle by the persona count is what turned that from a theoretical shape into a routine one.
* New suite `test-personas.sh`. It runs **two** cycles where `test-providers.sh` runs one, because a single cycle produces no resumed invocation and the resumed invocation is where the most important assertion lives. `test-providers.sh` pins one persona in its baseline so its 71 cases keep asserting exactly one invocation each.

## 0.0.5 - 2026-08-04

* Default prompts now tell the reviewer how to judge the tests a PR adds. "Pay attention to test quality" was already in there and wasn't enough: a review passed a PR whose new tests passed identically with the production change reverted — real tests, readable, worthless as regression protection, and nothing said about them. The problem is that "is this a good test?" resolves to "it looks like the other tests," so the stanza states a procedure instead. For each added or modified test: work out which lines of the non-test change it depends on, mentally revert just those, and decide whether it would still pass — if so, raise it, naming the surviving mutation. Then the neighbouring mutations (a boundary moved by one, a negated condition, a deleted error branch, an emptied collection, a constant return), and the as-implemented smells — assertions that restate the implementation, recompute the expected value with the same logic the code uses, assert a mock's own stubbed return, or freeze current output as a snapshot with no statement of what's required. Plus tests that cannot fail, and names that promise what the body never checks. Defaults only, like the other stanzas, and repeated in the followup: tests added in response to earlier findings arrive on *resumed* passes, which are exactly the ones whose earliest turns a context summary has already dropped.
* Default prompts now tell the reviewer how to use `gh` under a privilege-minimized token, because two natural commands cannot work with one. A bare `gh pr view` implicitly fetches `statusCheckRollup`, and no fine-grained PAT permission grants it, so the command fails outright — and `gh pr checks` needs the same permission and cannot work at all. The failure reads like a broken token rather than a missing permission, and a session that burns its opening tool calls on it tends to start guessing at the diff instead of reading it. So the defaults name the working invocation (`gh pr view N --json <explicit field list>`), rule out `gh pr checks`, and state plainly that CI status is unavailable so the reviewer judges the code rather than waiting on a build. Repeated in the followup prompt rather than left to the session's own history, since a long-resumed session's earliest turns are the first thing a context summary drops. Applies to the **defaults only**, like the Linear stanza: an operator-supplied `REVIEW_PROMPT`/`FOLLOWUP_PROMPT` still reaches Claude verbatim, so carry the constraints over yourself or add them via the `_SUFFIX` variables. Four new test cases (70 total), with `ARGV:`/`NOARGV:` assertion forms for the prompt claude was actually handed.
* `PROVIDER=workersai` also runs the **Kimi** models now. LiteLLM omits the `content` key entirely on an assistant message that carries only `tool_calls` — valid OpenAI, accepted by glm-5.2, and rejected outright by Kimi with `Invalid value at messages[N].content: Invalid input`. Claude Code emits exactly that message on every tool call, so those models failed on essentially every review pass. Confirmed by sending Cloudflare two otherwise byte-identical bodies: without the key 400, with `content: ""` 200. The fix is a new `workersai-shim.py` — ~150 lines of Python standard library — that runs between the translator and Cloudflare and fills the field in. It has to be a separate process because the omission is in LiteLLM's *output*, past the point its own plugin hooks can reach; `modify_params` does not do it and no setting does, while the two provider prefixes that would (`deepseek/`, `mistral/`) also drop the tool-role message and rewrite `tool_choice` respectively. Like the translator it is loopback-only, started synchronously before the thing that talks to it, and watched each cycle. It is unconditional for this provider (`SHIM_NORMALIZE=0` removes the hop) rather than per-model, since an empty string is valid for every model and one always-exercised path beats a special case. New suite `test-shim.sh` runs the real script against a local echo server — no Docker, network, or credentials — and covers the injection, its restraint, the loopback bind, and the fact that a streamed response is relayed as it arrives: the first version used `read()` instead of `read1()` and buffered whole completions to the end, which is indistinguishable from a hung reviewer.
* Add `PROVIDER=workersai`, which runs **Cloudflare Workers AI** models — `@cf/zai-org/glm-5.2` (the default), `@cf/moonshotai/kimi-k2.7-code`, and the rest of the catalog. Those models are served only over an OpenAI-compatible schema, and Cloudflare's docs are explicit that the Anthropic-shaped `/ai/v1/messages` endpoint does not serve them, so `PROVIDER=cloudflare` can never reach them. This arm bridges the gap with a **LiteLLM proxy bundled in the image** and run on loopback as an Anthropic→OpenAI translator, streaming and tool calls included. Configuration is two variables — `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_API_TOKEN` — because the endpoint is derived from the account. The Cloudflare token stays behind the translator: Claude Code gets a random per-container key instead, so a prompt-injected review cannot read the real credential out of its environment. The translator is bound to `127.0.0.1` (its own default is `0.0.0.0`), started synchronously so no review pass runs before it answers, and re-checked each cycle so a dead one is a loud error rather than a silently failing loop. Bundling it roughly doubles the image, from ~1.1GB to ~1.9GB. The generated config sets `use_chat_completions_url_for_anthropic_messages`, which is required rather than optional: LiteLLM otherwise translates `/v1/messages` into the OpenAI *Responses* API, which Cloudflare does not serve for these models, and every request fails its schema union — reported as a wall of per-tool complaints that misdirects entirely from the real fault (a Responses-shaped body with no `messages`). `LITELLM_DEBUG=1` logs the translated bodies for diagnosing the next one of these; it includes credentials, so it warns and stays off by default. Note that `litellm[proxy]` under-constrains `fastapi`, which dropped a symbol litellm imports in a *patch* release (0.140.7) — so fastapi is pinned, and the build now fails fast on an unimportable proxy instead of shipping an image that starts and never serves.
* Add `PROVIDER=cloudflare` for a Cloudflare AI Gateway, covering every environment variable on Cloudflare's Claude Code integration page. `GATEWAY_UPSTREAM` (`anthropic` | `bedrock` | `vertex`) says which upstream the gateway fronts, since Claude Code speaks to each differently: `anthropic` takes `ANTHROPIC_BASE_URL` plus an API key or Bearer token, `bedrock` takes `ANTHROPIC_BEDROCK_BASE_URL`, and `vertex` takes `ANTHROPIC_VERTEX_BASE_URL` + `ANTHROPIC_VERTEX_PROJECT_ID` + `CLOUD_ML_REGION`. `REVIEW_MODEL` is required (all three name models differently).
* This is a gateway-only path on purpose: the gateway holds the cloud credentials, so the entrypoint sets `CLAUDE_CODE_USE_BEDROCK`/`CLAUDE_CODE_USE_VERTEX` and `CLAUDE_CODE_SKIP_BEDROCK_AUTH`/`CLAUDE_CODE_SKIP_VERTEX_AUTH` itself. A switch that contradicts `GATEWAY_UPSTREAM`, or one asking Claude Code to authenticate to AWS/GCP directly, is a startup error rather than a silent override — and the bedrock/vertex arms drop any leftover `ANTHROPIC_BASE_URL`/`_API_KEY`/`_AUTH_TOKEN` so a stale key can't confuse which endpoint is in use.
* Tolerate quoted env-file values. `docker run --env-file` does no shell quote processing, so `ANTHROPIC_BASE_URL="https://..."` arrived with literal quotes and every request then failed on an unparseable URL — late, and nowhere near the real cause. The entrypoint now strips one matched surrounding pair from the operator-supplied variables (with a warning) and rejects a base URL that isn't `http(s)://` at startup instead. The quoted `PR_SEARCH` example in `.env.example`/`README.md` was itself wrong, and is fixed.
* Add `test-providers.sh`, the project's first test suite: 46 cases over the provider-selection block, asserting either the startup error each misconfiguration refuses with or the exact environment the entrypoint hands `claude`. No Docker, network, or credentials needed — `gh`/`git`/`claude`/`sleep` are stubbed. Run `./test-providers.sh`, or pass a substring to filter by case label.
* Support `ANTHROPIC_CUSTOM_HEADERS` on **any** provider (a gateway can front a custom or Ollama endpoint too). It carries the `cf-aig-authorization` gateway token, and on the bedrock/vertex upstreams — where Claude Code's own cloud auth is skipped — it is the only credential there is, so it's required for those two.
* Make it possible to send **several** custom headers. Claude Code takes them as one multi-line value, which an env file cannot express at all (one `KEY=VALUE` per line, no continuation, no escape processing), so the entrypoint now accepts two one-line spellings and assembles the multi-line value itself: a literal `\n` between headers, and/or `ANTHROPIC_CUSTOM_HEADERS_1`…`_20`. Only `\n` is translated, so a backslash inside a token survives; each line is validated separately, and an error names the header but never its value.
* Reject a base URL that already ends in an endpoint path (`/v1/messages`, `/v1/chat/completions`, `/v1/responses`, `/v1/complete`) at startup. Claude Code appends `/v1/messages` to the base URL itself, so pasting the full endpoint from a `curl` example yields a doubled path and a 404 on every request, reported as an unhelpful "No route for that URI". A bare trailing `/v1` is still allowed — the Vertex base URL needs one.
* `GATEWAY_UPSTREAM` is now optional, defaulting to `anthropic` — the one upstream where it selects nothing (no switches to flip, and the base URL and credential are the ordinary `ANTHROPIC_*` ones). `bedrock` and `vertex` still have to be named.

## 0.0.4 - 2026-07-30

* Review each PR in its own Claude Code session. The harness now enumerates candidate PRs and iterates, giving each PR an independent, resumable session so re-reviews avoid duplicate comments per PR. `MAX_PASSES_PER_SESSION` now applies per PR.
* Add PR targeting — choose exactly one of: all open PRs (`--all` / `PR_ALL`), open PRs assigned to a user (`--assignee` / `PR_ASSIGNEE`), a specific set of PR numbers (`--prs` / `PR_IDS`), or a `gh` search query (`--search` / `PR_SEARCH`). Zero or more than one is a startup error.
* Prompts are now PR-scoped: `REVIEW_PROMPT` (session start) and `FOLLOWUP_PROMPT` (resume) substitute a `{{PR}}` token with the PR number; custom prompts use the same token.
* Launcher: infer the env file (`.env.claudebox` preferred over `.env`) and repo from the current directory, derive a per-repo container name `claudebox--<org>--<repo>` so several claudeboxes can run at once, announce those inferences loudly, and add `--tail` to follow logs right after `run`.
* Optional Linear ticket context: set `LINEAR_API_KEY` and the reviewer reads the Linear ticket a PR references — description and comments — and flags where the change diverges from what the ticket asked for. Use a read-only key; the reviewer runs with permissions skipped.
* Always run review passes with `--strict-mcp-config`, so a repository under review can't inject MCP servers of its own choosing into a permission-skipped session.
* Add `REVIEW_PROMPT_SUFFIX`/`FOLLOWUP_PROMPT_SUFFIX` to append extra instructions to whichever prompt is in effect (default or an operator override), without replacing it.

## 0.0.3 - 2026-07-17
