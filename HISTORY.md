# History

## 0.2.0 - 2026-08-25

* **A correction.** advocate's personas are *plan-review* personas: they were written to interrogate a proposal before the work happens. 0.1.0 shipped them as the mechanism for reviewing pull requests in general, which misread what they are for. Sage asking whether the fundamental approach is sound, and SME asking whether the problem is correctly understood, cost almost nothing to act on before code exists, and on a finished PR the only honest answer to either is "start over". So review **mode** is now a first-class axis alongside PR and persona, and claudebox does both jobs.
* A plan arrives as a pull request whose diff is the plan document, which is what keeps the change small: the loop, the four PR selectors, the session map, the usage-limit handling and the `gh pr comment` output channel are all untouched. A PR carrying `PLAN_LABEL` (default `plan`) is reviewed in plan mode; every other PR is code mode, so an operator who never labels anything sees exactly 0.1.0's behavior. Routing is by label rather than by a path heuristic or a classifier pass: a label is explicit, per-PR, author-controlled, and puts no nondeterministic decision inside the harness's control flow.
* Mode is decided inside `enumerate_candidate_prs`, which now emits `number<TAB>mode` so nothing downstream asks GitHub a second time. For `PR_ALL`/`PR_ASSIGNEE`/`PR_SEARCH` the labels ride along in the `gh pr list` call already being made; `PR_IDS` has no list call behind it, so it costs one `gh pr view` per PR per cycle.
* **A failed label lookup skips that PR for the cycle**, with a WARN, and never falls back to code mode. This is the decision most likely to be questioned later, so: a wrong-mode review posts real comments on a real PR and cannot be taken back, where a skip is one log line and a retry on the next cycle. The `ids` arm checks its output is non-empty rather than trusting an exit status, because a `gh` that exits 0 with nothing useful would otherwise drop the PR with no warning at all.
* `PERSONA_DIR` is now a parent holding `code/` and `plan/`, each with its own `_shared.md` and all six persona bodies. Both trees resolve at startup whether or not any PR is labeled, so a broken plan persona kills the container at boot instead of surfacing the first time somebody adds a label. A flat `PERSONA_DIR` is a hard startup error naming the layout it expected; this breaks 0.1.0's mount-your-own contract, and nothing has shipped off that contract.
* Per-mode defaults: code keeps `red_team,adversarial,sme,sage` and plan runs all six, selected by `PERSONAS` and `PLAN_PERSONAS`. The code cut needs no new argument, since it is the reasoning 0.1.0 already wrote down: `user` and `good_friend` were authored against designs and whole projects, and plan review is where they finally have something to bite on.
* Session keys grew a segment, `"$pr:$mode:$persona"`, so a PR whose label changes orphans its old sessions and starts fresh under the new mode. That is intended: a code-mode session's accumulated history is the wrong context for reviewing the same branch as a plan. `--resume` matters more in plan mode than in code mode, because feedback on a plan produces a revised plan pushed to the same branch, and a persona reading revision two in the context of what it said about revision one is exactly the shape the loop was already built for.
* Plan prompts drop the test stanza (there is no implementation to mutate), keep the gh and Linear stanzas, and add a plan stanza that says what **not** to flag as well as what to review: a code-shaped reviewer handed a design document will otherwise report missing error handling in code nobody has written. Overrides are `PLAN_REVIEW_PROMPT`, `PLAN_FOLLOWUP_PROMPT`, and their `_SUFFIX` forms; the bare names still mean code mode. Neither the four code prompt variables nor their plan counterparts is quote-stripped, since a quote at either end of free text can be content; the code four were never on that list, and the plan four were taken back off it to match.
* **The importer writes the same body into both trees, and there is deliberately no divergence detection.** The second decision worth flagging for later. advocate has one body per persona, so `tools/import-advocate-personas.py` cannot invent two, and a hand edit in one tree is something a re-import would clobber. Its docstring already says to run it once and commit the output, so a re-run produces a diff that gets reviewed before it is committed, and a hand edit shows up in that diff as a reverted line to keep. A detector buys very little over reading a diff somebody was going to read anyway.

## 0.1.0 - 2026-08-21

* Reviews now run as **adversarial personas** rather than as one generalist reviewer, borrowed from [advocate](https://github.com/jmcentire/advocate) — Red Team (survive assault), Adversarial (hold under challenge), Sage (simplify), Subject Matter Expert (peer sign-off), and opt-in User (navigate it cold) and Good Friend (the 3am test). advocate itself cannot be used here: it calls provider APIs directly, so it cannot run against a fixed-price plan, which is the whole reason claudebox drives the CLI. Definitions ship as files (`personas/*.md`, `PERSONA_DIR`) imported by a committed script, with advocate's JSON output contract stripped (claudebox posts `gh` comments) and its "silence from you is a strong signal" rule kept. `--persona` / `PERSONAS` selects the set; an unknown name is a startup error, because a typo that silently narrowed the review to one persona would read as a working run.
* One session per PR **per persona** (`PR_SESSION` keyed `pr:persona`, so `MAX_PASSES_PER_SESSION` rotates per pair). The persona travels in `--append-system-prompt`, which keeps an operator-supplied `REVIEW_PROMPT` verbatim, and is re-passed on every single pass: measured, the flag does **not** survive `--resume`, so passing it once would make cycle one adversarial and every cycle after it the old generalist wearing a persona's name in the log.
* Personas are blind to each other, deliberately. Nothing tells a persona to skip what another already raised: that anchors it to a review it did not do, and avoiding that flavour of group-think is why this tool exists. Two angles of attack hitting the same thing is a signal it deserves two comments. Comments are signed `-claudebox (<Persona>)`.
* Usage and rate limits are now a distinct failure. A pass that hits one keeps its session, ends the cycle instead of walking the remaining personas into the same wall, and waits `LIMIT_BACKOFF_SECONDS` (default 1800). The old path dropped the session, which under a limit meant the next cycle re-read every PR and re-posted findings already posted — spending more of the allowance that had just run out. Multiplying sessions per cycle by the persona count is what turned that from a theoretical shape into a routine one.
* New suite `test-personas.sh`. It runs **two** cycles where `test-providers.sh` runs one, because a single cycle produces no resumed invocation and the resumed invocation is where the most important assertion lives. `test-providers.sh` pins one persona in its baseline so its 71 cases keep asserting exactly one invocation each.

## 0.0.5 - 2026-08-04

* Default prompts now tell the reviewer how to judge the tests a PR adds. "Pay attention to test quality" was already in there and wasn't enough: a review passed a PR whose new tests passed identically with the production change reverted — real tests, readable, worthless as regression protection, and nothing said about them. The problem is that "is this a good test?" resolves to "it looks like the other tests," so the stanza states a procedure instead. For each added or modified test: work out which lines of the non-test change it depends on, mentally revert just those, and decide whether it would still pass — if so, raise it, naming the surviving mutation. Then the neighbouring mutations (a boundary moved by one, a negated condition, a deleted error branch, an emptied collection, a constant return), and the as-implemented smells — assertions that restate the implementation, recompute the expected value with the same logic the code uses, assert a mock's own stubbed return, or freeze current output as a snapshot with no statement of what's required. Plus tests that cannot fail, and names that promise what the body never checks. Defaults only, like the other stanzas, and repeated in the followup: tests added in response to earlier findings arrive on *resumed* passes, which are exactly the ones whose earliest turns a context summary has already dropped.
* Default prompts now tell the reviewer how to use `gh` under a privilege-minimized token, because two natural commands cannot work with one. A bare `gh pr view` implicitly fetches `statusCheckRollup`, and no fine-grained PAT permission grants it, so the command fails outright — and `gh pr checks` needs the same permission and cannot work at all. The failure reads like a broken token rather than a missing permission, and a session that burns its opening tool calls on it tends to start guessing at the diff instead of reading it. So the defaults name the working invocation (`gh pr view N --json <explicit field list>`), rule out `gh pr checks`, and state plainly that CI status is unavailable so the reviewer judges the code rather than waiting on a build. Repeated in the followup prompt rather than left to the session's own history, since a long-resumed session's earliest turns are the first thing a context summary drops. Applies to the **defaults only**, like the Linear stanza: an operator-supplied `REVIEW_PROMPT`/`FOLLOWUP_PROMPT` still reaches Claude verbatim, so carry the constraints over yourself or add them via the `_SUFFIX` variables. Four new test cases (70 total), with `ARGV:`/`NOARGV:` assertion forms for the prompt claude was actually handed.
* `PROVIDER=workersai` also runs the **Kimi** models now. LiteLLM omits the `content` key entirely on an assistant message that carries only `tool_calls` — valid OpenAI, accepted by glm-5.2, and rejected outright by Kimi with `Invalid value at messages[N].content: Invalid input`. Claude Code emits exactly that message on every tool call, so those models failed on essentially every review pass. Confirmed by sending Cloudflare two otherwise byte-identical bodies: without the key 400, with `content: ""` 200. The fix is a new `workersai-shim.py` — ~150 lines of Python standard library — that runs between the translator and Cloudflare and fills the field in. It has to be a separate process because the omission is in LiteLLM's *output*, past the point its own plugin hooks can reach; `modify_params` does not do it and no setting does, while the two provider prefixes that would (`deepseek/`, `mistral/`) also drop the tool-role message and rewrite `tool_choice` respectively. Like the translator it is loopback-only, started synchronously before the thing that talks to it, and watched each cycle. It is unconditional for this provider (`SHIM_NORMALIZE=0` removes the hop) rather than per-model, since an empty string is valid for every model and one always-exercised path beats a special case. New suite `test-shim.sh` runs the real script against a local echo server — no Docker, network, or credentials — and covers the injection, its restraint, the loopback bind, and the fact that a streamed response is relayed as it arrives: the first version used `read()` instead of `read1()` and buffered whole completions to the end, which is indistinguishable from a hung reviewer.
* Add `PROVIDER=workersai`, which runs **Cloudflare Workers AI** models — `@cf/zai-org/glm-5.2` (the default), `@cf/moonshotai/kimi-k2.7-code`, and the rest of the catalog. Those models are served only over an OpenAI-compatible schema, and Cloudflare's docs are explicit that the Anthropic-shaped `/ai/v1/messages` endpoint does not serve them, so `PROVIDER=cloudflare` can never reach them. This arm bridges the gap with a **LiteLLM proxy bundled in the image** and run on loopback as an Anthropic→OpenAI translator, streaming and tool calls included. Configuration is two variables — `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_API_TOKEN` — because the endpoint is derived from the account. The Cloudflare token stays behind the translator: Claude Code gets a random per-container key instead, so a prompt-injected review cannot read the real credential out of its environment. The translator is bound to `127.0.0.1` (its own default is `0.0.0.0`), started synchronously so no review pass runs before it answers, and re-checked each cycle so a dead one is a loud error rather than a silently failing loop. Bundling it roughly doubles the image, from ~1.1GB to ~1.9GB. The generated config sets `use_chat_completions_url_for_anthropic_messages`, which is required rather than optional: LiteLLM otherwise translates `/v1/messages` into the OpenAI *Responses* API, which Cloudflare does not serve for these models, and every request fails its schema union — reported as a wall of per-tool complaints that misdirects entirely from the real fault (a Responses-shaped body with no `messages`). `LITELLM_DEBUG=1` logs the translated bodies for diagnosing the next one of these; it includes credentials, so it warns and stays off by default. Note that `litellm[proxy]` under-constrains `fastapi`, which dropped a symbol litellm imports in a *patch* release (0.140.7) — so fastapi is pinned, and the build now fails fast on an unimportable proxy instead of shipping an image that starts and never serves.
* Add `PROVIDER=cloudflare` for a Cloudflare AI Gateway, covering every environment variable on Cloudflare's Claude Code integration page. `GATEWAY_UPSTREAM` (`anthropic` | `bedrock` | `vertex`) says which upstream the gateway fronts, since Claude Code speaks to each differently: `anthropic` takes `ANTHROPIC_BASE_URL` plus an API key or Bearer token, `bedrock` takes `ANTHROPIC_BEDROCK_BASE_URL`, and `vertex` takes `ANTHROPIC_VERTEX_BASE_URL` + `ANTHROPIC_VERTEX_PROJECT_ID` + `CLOUD_ML_REGION`. `REVIEW_MODEL` is required (all three name models differently).
* This is a gateway-only path on purpose: the gateway holds the cloud credentials, so the entrypoint sets `CLAUDE_CODE_USE_BEDROCK`/`CLAUDE_CODE_USE_VERTEX` and `CLAUDE_CODE_SKIP_BEDROCK_AUTH`/`CLAUDE_CODE_SKIP_VERTEX_AUTH` itself. A switch that contradicts `GATEWAY_UPSTREAM`, or one asking Claude Code to authenticate to AWS/GCP directly, is a startup error rather than a silent override — and the bedrock/vertex arms drop any leftover `ANTHROPIC_BASE_URL`/`_API_KEY`/`_AUTH_TOKEN` so a stale key can't confuse which endpoint is in use.
* Tolerate quoted env-file values. `docker run --env-file` does no shell quote processing, so `ANTHROPIC_BASE_URL="https://..."` arrived with literal quotes and every request then failed on an unparseable URL — late, and nowhere near the real cause. The entrypoint now strips one matched surrounding pair from the operator-supplied variables (with a warning) and rejects a base URL that isn't `http(s)://` at startup instead. The quoted `PR_SEARCH` example in `.env.example`/`README.md` was itself wrong, and is fixed.
* Add `test-providers.sh`, the project's first test suite: 46 cases over the provider-selection block, asserting either the startup error each misconfiguration refuses with or the exact environment the entrypoint hands `claude`. No Docker, network, or credentials needed — `gh`/`git`/`claude`/`sleep` are stubbed. Run `./test-providers.sh`, or pass a substring to filter by case label.
* Support `ANTHROPIC_CUSTOM_HEADERS` on **any** provider (a gateway can front a custom or Ollama endpoint too). It carries the `cf-aig-authorization` gateway token, and on the bedrock/vertex upstreams — where Claude Code's own cloud auth is skipped — it is the only credential there is, so it's required for those two.
* Make it possible to send **several** custom headers. Claude Code takes them as one multi-line value, which an env file cannot express at all (one `KEY=VALUE` per line, no continuation, no escape processing), so the entrypoint now accepts two one-line spellings and assembles the multi-line value itself: a literal `\n` between headers, and/or `ANTHROPIC_CUSTOM_HEADERS_1`…`_20`. Only `\n` is translated, so a backslash inside a token survives; each line is validated separately, and an error names the header but never its value.
* Reject a base URL that already ends in an endpoint path (`/v1/messages`, `/v1/chat/completions`, `/v1/responses`, `/v1/complete`) at startup. Claude Code appends `/v1/messages` to the base URL itself, so pasting the full endpoint from a `curl` example yields a doubled path and a 404 on every request, reported as an unhelpful "No route for that URI". A bare trailing `/v1` is still allowed — the Vertex base URL needs one.
* `GATEWAY_UPSTREAM` is now optional, defaulting to `anthropic` — the one upstream where it selects nothing (no switches to flip, and the base URL and credential are the ordinary `ANTHROPIC_*` ones). `bedrock` and `vertex` still have to be named.

## 0.0.4 - 2026-07-30

* Review each PR in its own Claude Code session. The harness now enumerates candidate PRs and iterates, giving each PR an independent, resumable session so re-reviews avoid duplicate comments per PR. `MAX_PASSES_PER_SESSION` now applies per PR.
* Add PR targeting — choose exactly one of: all open PRs (`--all` / `PR_ALL`), open PRs assigned to a user (`--assignee` / `PR_ASSIGNEE`), a specific set of PR numbers (`--prs` / `PR_IDS`), or a `gh` search query (`--search` / `PR_SEARCH`). Zero or more than one is a startup error.
* Prompts are now PR-scoped: `REVIEW_PROMPT` (session start) and `FOLLOWUP_PROMPT` (resume) substitute a `{{PR}}` token with the PR number; custom prompts use the same token.
* Launcher: infer the env file (`.env.claudebox` preferred over `.env`) and repo from the current directory, derive a per-repo container name `claudebox--<org>--<repo>` so several claudeboxes can run at once, announce those inferences loudly, and add `--tail` to follow logs right after `run`.
* Optional Linear ticket context: set `LINEAR_API_KEY` and the reviewer reads the Linear ticket a PR references — description and comments — and flags where the change diverges from what the ticket asked for. Use a read-only key; the reviewer runs with permissions skipped.
* Always run review passes with `--strict-mcp-config`, so a repository under review can't inject MCP servers of its own choosing into a permission-skipped session.
* Add `REVIEW_PROMPT_SUFFIX`/`FOLLOWUP_PROMPT_SUFFIX` to append extra instructions to whichever prompt is in effect (default or an operator override), without replacing it.

## 0.0.3 - 2026-07-17

* Generalize the backend beyond Ollama Cloud: a new `PROVIDER` env var (`ollama` | `anthropic` | `custom`) selects the model provider. `ollama` remains the default, so existing configs are unchanged; `anthropic` targets Anthropic's own API, and `custom` targets any Anthropic-compatible endpoint. Every model tier is still pinned to the one `REVIEW_MODEL`.
* `PROVIDER=anthropic` no longer requires an `ANTHROPIC_API_KEY`: it falls back to `CLAUDE_CODE_OAUTH_TOKEN` (from `claude setup-token`) or a mounted `~/.claude` credentials file, so you can reuse your existing `claude` login instead of a separate key.
* Add a `claudebox.sh` launcher that wraps `docker build`/`run` and the lifecycle commands (`build`, `run`, `test`, `logs`, `shell`, `stop`, `status`) with the required hardening flags baked in. Self-describing via `--help`; `--dry-run` prints the docker command without executing, and `--mount-claude` bind-mounts `~/.claude` for Anthropic login reuse.
* Move the provider-specific `REVIEW_MODEL` default out of the Dockerfile so each provider can supply its own (ollama: `glm-5.2:cloud`, anthropic: `claude-opus-4-8`).
* Tweak the default prompt to encourage a slightly bigger-picture perspective.
